# deep-interview 해부 — 모호도를 숫자로 만드는 법과, 그 숫자를 믿을 수 없는 이유

- 작성일: 2026-08-28
- 분석 대상: `references/gajae-code` (`v0.13.2`) 의 `deep-interview` 스킬 + 런타임, `references/ouroboros` (`v0.51.4`) 의 `deterministic_floor`
- 성격: 연구 노트 + 설계 토론 기록. 앞의 두 문서가 "하네스에 무엇을 넣는가"와 "그중 무엇이 스킬이 되는가"를 다뤘다면, 이 문서는 **하나의 실제 하네스를 끝까지 해부하고, 그 핵심 메커니즘(모호도 채점)의 인식론적 결함을 짚은 뒤, 미시경제학의 현시선호이론으로 대안을 제시**한다.

## 1. 한 문장 요약

> **deep-interview는 "모호함"을 0~1 실수로 만들어 그 값이 임계값 아래로 떨어지기 전까지 모든 mutation을 차단하는 요구사항 하네스다. 그런데 그 실수는 LLM이 스스로 매긴 기수적(cardinal) 자기평가이고, 시스템이 실제로 쓰는 것은 그 값의 순서(ordinal)뿐이다. 이 불일치가 이 설계의 가장 큰 개선 여지이며, 경제학은 90년 전에 같은 문제를 현시선호이론으로 해결했다.**

## 2. deep-interview란 무엇인가 `[gjc]`

### 2.1 정체

Socratic 질문으로 모호한 아이디어를 명세로 바꾸는 워크플로. 프론트매터가 성격을 다 드러낸다:

```yaml
name: deep-interview
pipeline: [deep-interview, ralplan]
handoff-policy: approval-required
handoff: .gjc/_session-{sessionid}/specs/deep-interview-{slug}.md
level: 3
```

`source` 필드에 상류가 명시돼 있다 — Ouroboros 프로젝트에서 포크. SKILL.md 본문은 그 동기를 이렇게 적는다: 기존 단일 패스 기획(analyst + architect)은 **"무엇을 원하냐"고 묻지 "무엇을 가정하고 있냐"고 묻지 않아서** 진짜 모호한 입력에서 무너진다.

### 2.2 분량 분포 — 왜 "shallow skill"이 아닌가

| 구성 | 라인 수 |
| --- | --- |
| `SKILL.md` (모델용 지침) | 1,046 |
| 프롬프트 fragment 3개 (auto-research / auto-answer / lateral-panel) | 126 |
| TypeScript 런타임 (state / stage / recorder / runtime / ambiguity / gate / middleware) | 약 4,500 |
| 전용 테스트 파일 | 15개 (redteam 3개 포함) |

**산문 대비 코드가 4배가 넘는다.** 이것이 "지침만 담긴 스킬"과 "하네스"를 가르는 1차 지표다.

### 2.3 역할 분담 — 이 설계의 정답인 부분 `[gjc]`

`deep-interview-runtime.ts` 헤더 주석이 경계선을 명시적으로 그어둔다:

| 층 | 담당 | 자유도 |
| --- | --- | --- |

## 3. 하네스가 강제하는 6가지 `[gjc]`

### 3.1 결정론적 모호도 하한선 (deterministic ambiguity floor)

LLM이 보고한 모호도 점수를 **믿지 않는다.** 런타임이 저장된 상태만 보고 독립적으로 하한을 계산해 `max(reported, floor)`로 clamp한다.

```
floor = 0.10 × (superseded_by 없는 disputed established fact 수)    # 모순 압력
      + 0.05 × (goal/constraints/criteria 미채점 active 컴포넌트 수)  # 공백 압력
      + 0.05 × (auto-answered rounds / scored rounds)               # 가정 희석
```

코드 주석이 이유를 명시한다 — *"LLM scorer는 이전 점수에 anchoring해서, 사용자가 pivot하거나 모순을 일으켰을 때 상승분을 under-report한다."*

**세 항 모두 판단이 아니라 계수(counting)라는 점이 핵심이다.** 몇 개인지는 세면 나온다.

효과: 기본 임계값이 0.05인데 **미해결 모순 사실 하나면 floor가 0.10** → 모순이 해소되기 전에는 수렴이 수학적으로 불가능. 해소 경로도 코드가 강제한다 — 재확인(`disputed: false`)이거나 새 사실 + `superseded_by` 연결이거나. **hard delete는 델타 병합 레벨에서 불가능하다.**

`current_ambiguity`는 runtime-owned라 모델이 직접 못 쓴다. `apply`/`write` 시점에 런타임이 유도·clamp하고, 모델은 명령 출력에서 읽어가야 한다.

### 3.2 상류 대조 — 계수는 같고 세는 대상만 다르다 `[ouro]` `[gjc]` `[도출]`

ouroboros 원본 [`src/ouroboros/auto/grading.py`](../../references/ouroboros/src/ouroboros/auto/grading.py):

```python
floor = 0.05 * open_gap_count      # 미완료 required section
      + 0.10 * conflicting_count    # CONFLICTING 엔트리
      + 0.05 * assumption_ratio     # 가정에만 기댄 section 비율
```

gajae-code 버전과 **계수(0.05 / 0.10 / 0.05)와 세 항의 의미론(공백 / 모순 / 증거 희석)이 완전히 동일**하고, 세는 대상만 각자의 상태 모델로 갈아끼웠다.

`[도출]` 이것이 하네스 규칙의 이식 단위가 무엇인지 보여준다. **이식되는 것은 "공백·모순·증거희석에 각각 압력을 매긴다"는 구조이지 구체적 필드가 아니다.** 우리 프로젝트에 옮길 때도 필드가 아니라 이 세 축을 옮겨야 한다.

### 3.3 양방향(non-monotonic) 채점

"점점 명확해진다"를 가정하지 않는다. 상승 트리거 4종:

| | 트리거 | 예 |
| --- | --- | --- |
| A | 확립된 사실과 직접 모순 | 3라운드 "승인 1명" → 7라운드 "2명 필요" |
| B | 양립 불가능한 요구 | "완전 오프라인" + "실시간 협업 코멘트" |
| C | 회피/저품질 답변 | "알아서 적당히" |
| D | 스코프 확장 | 8라운드에 "슬랙 알림도" |

별도 페널티 항을 두지 않고 **해당 축 점수를 낮춰서** 기존 가중합 공식이 모호도를 올리게 한다. 그리고 **TRANSITION VALIDATION**: 트리거가 보고되면 해당 축은 개선될 수 없고 전체 모호도는 반드시 상승해야 한다 (명시적 disputed/unresolved + 사유 제외).

상승은 **silent** — 모달도, 강제 해결 단계도, 전용 충돌 UI도 없다. 다음 질문이 그쪽을 겨냥할 뿐.

### 3.4 Round 0 토폴로지 게이트 + intent contract

**깊이우선 질문의 구조적 약점**을 겨냥한 장치. 사용자가 가장 자세히 설명한 컴포넌트가 형제를 잡아먹는 문제.

SKILL.md에 fixture가 박혀 있다 — "CSV 인제스트 → 정규화 → 리뷰어 UI → 감사 리포트" 예시에서 *"자세히 설명된 `Review UI`가 덜 설명된 형제를 붕괴시키거나 대체해서는 안 된다."*

추출 규칙:

- **독립적으로 성공/실패할 수 있는 결과물**만 최상위 컴포넌트
- 1~6개, 초과 시 상위 수준으로 묶고 사유 기록
- **구현 태스크나 필드는 컴포넌트가 아니다** (사용자가 독립 결과물로 프레이밍하지 않는 한)

첫 채점 **전에** 사용자에게 한 번 확인하고 잠근다. 여기에 `intent_contract`가 붙는다: `artifact:` / `surface:` / `integration:` / `constraint:` 4카테고리 접두 ID → canonical sort → SHA-256 manifest digest → 답변 해시 바인딩. **recorder만 쓸 수 있고 모델 payload로 들어오면 스트립된다.**

최종 spec에서 잠긴 ID가 빠지면 intent-review 질문이 강제되고, 명시적 승인 옵션 없이는 **spec 저장과 handoff가 fail-closed**. 조용한 스코프 축소 차단.

잠근 뒤의 효과 3가지:

1. 컴포넌트별 독립 채점 — 전체 점수는 각 축의 **최약 컴포넌트 점수**
2. 질문 대상 로테이션 (`last_targeted_component_id`)
3. 미채점 컴포넌트가 floor를 밀어올림 (§3.1의 두 번째 항)

### 3.5 `ask` 툴 우회 차단

모델이 `Question:` / `Options:` 블록을 산문으로 출력해 구조화 `ask` 호출을 건너뛰는 것을 코드가 탐지한다. [`plaintext-gate-guard.ts`](../../references/gajae-code/packages/coding-agent/src/deep-interview/plaintext-gate-guard.ts)가 3신호(Options 헤딩 + 재진술 의도 + deep-interview 맥락)를 정규식 매칭하고, 한국어 패턴(`재진술`, `확정`, `맞습니까`)까지 포함한다.

**왜 중요한가:** `ask`를 거쳐야만 recorder가 answer hash를 만들고 라운드가 기록된다. 산문으로 물으면 상태에 아무것도 안 남는다. **우회 = 감사 추적 소멸.**

### 3.6 트랜잭션 상태 쓰기

`stage --for <transition>` → `check` (dry-run) → `apply` (revision CAS) → `discard`. 델타만 전송:

| transition | 병합 규칙 |
| --- | --- |
| `record-round` | 라운드 1개, `round_key`로 병합. `scored` → `answered` downgrade 불가 |
| `update-facts` | `id`로 필드 병합. **델타가 fact를 hard-delete 불가** |
| `merge-state` | 변경 필드만 shallow merge (`null`은 키 삭제) |

lifecycle 키(`state_revision`, `receipt`, `updated_at` 등)는 모델이 넣어도 스트립되고 `ignored_runtime_owned_keys`로 리포트된다. 전체 transcript 재전송은 "낭비이자 race"로 금지.

### 3.7 입력 안전성의 비대칭

`initial_context` / `user_response` / `goal` 등 free-text 필드는 **셸 메타문자를 injection으로 거부하지 않는다.** 산문에는 원래 들어가니까. 대신 문자 수 상한(50k / 10k / 100k)으로 DoS만 막고, ID·카테고리·해시 등 **구조 필드만 엄격 검증**.

`[도출]` **내용 검사(content inspection)가 아니라 경계 검사(bounds checking)로 간다**는 판단. 우리 프로젝트의 use case 텍스트에도 그대로 적용된다.

## 4. 프롬프트 층의 대화 역학 `[gjc]`

코드로 강제 못 하는 것을 SKILL.md가 규범으로 잡는다.

- **한 라운드 한 질문.** 배칭 금지 (얕은 답변 → 부정확한 채점)
- **최약 축 겨냥 + 왜 지금 병목인지 한 문장 명시.** 이 한 문장 규칙이 은근히 강력하다 — 이유를 못 대는 질문은 애초에 생성되지 않는다
- **사실 vs 결정 분리.** 사실(스택, 버전, 기존 패턴)은 코드를 읽어 **인용 확인** 형태로 제시. 결정(목표, 스코프, 트레이드오프)만 사용자에게. 애매하면 결정으로 취급
- **Dialectic rhythm guard.** 에이전트 자가해결 3연속이면 다음은 무조건 사람에게. *"인터뷰는 코드베이스가 아니라 인간과 하는 것"*
- **Refine gate.** 추론이 담긴 자유서술은 Decision / Reasoning / Constraints / Out of scope / Codebase context로 구조화하고 **해석 전문을 질문 본문에 렌더해서** 재확인. 해석을 안 보여주고 "맞아?"만 묻는 것은 hard error
- **Lateral review panel.** 모호도 band 전이 시 `researcher` / `contrarian` / `simplifier` (+ 스코프 변경 시 `architect`)를 **독립 컨텍스트로 병렬** 소환. 서로 anchoring 안 되게 각자 사본. 전부 read-only, 질문 추가 불가, 완료 선언 불가
- **Closure guard + Restate gate.** 수학이 통과해도 완료가 아님. *"수학은 준비됐다지만 {gap} 때문에 받아들이지 않겠다"*로 게이트를 뒤집을 수 있고, 전체를 한 문장으로 접어 확인

### 4.1 질문 스타일 표 — Socratic 질문의 조작적 정의

SKILL.md의 핵심 정의: **"질문은 기능 목록을 모으는 게 아니라 가정(ASSUMPTION)을 드러내야 한다."**

| 약한 축 | 질문 형태 | 예 |
| --- | --- | --- |
| 목표 | "정확히 무슨 일이 일어나나?" | "'정규화'라 하셨는데 이상 레코드가 오면 정확히 어떻게 되나요?" |
| 제약 | "경계가 어디인가?" | "오프라인 동작이 필요한가요, 연결을 전제해도 되나요?" |
| 기준 | "된 걸 어떻게 아나?" | "완성품을 보여드리면 뭘 보고 '이거야'라 하실까요?" |
| 맥락 | "기존과 어떻게 맞물리나?" | "`src/auth/`에 passport+JWT가 있는데, 확장인가 분기인가요?" |
| 개념 불안정 | "이게 근본적으로 뭔가?" | "Task/Project/Workspace 중 뭐가 핵심 개체인가요?" |

`[도출]` **기준 축의 질문 형태가 특히 좋다.** "성공 기준이 뭐예요?"는 아무도 대답 못 하지만, "완성품을 보면 뭘 보고 맞다고 하시겠어요?"는 누구나 대답할 수 있고 **그 답이 곧 테스트 명세다.** 우리 프로젝트의 수용 기준 도출에 그대로 쓸 수 있다.

### 4.2 온톨로지 안정도 — 이미 존재하는 서수 지표

매 라운드 엔티티(명사)를 추출해 이전 라운드와 비교:

```
stability_ratio = (stable + changed) / total_entities
```

이름만 바뀐 것(`changed`)은 **수렴으로 계산**한다 — 개념이 지속되면 이름이 흔들려도 수렴이라는 판단. 3라운드 정체(±0.05)거나 8라운드 후에도 0.30 초과면 존재론 질문으로 리프레임.

`[도출]` **이 지표에는 절대 척도 주장이 없다.** 엔티티 집합의 안정성만 재고 "품질 점수"를 매기지 않는다. §9.5에서 다시 다룬다 — 이 설계는 이미 서수적 수렴 지표를 갖고 있으면서 게이트로는 쓰지 않고 있다.

## 5. 절대 하지 않는 것 — 실행 분리 `[gjc]`

**deep-interview는 요구사항 에이전트이지 실행 에이전트가 아니다.**

인터뷰 중 코드 편집 / 워커 실행 / task·skill·ultragoal 착수 전면 금지. 사용자가 "구현 계획"이라 말해도 그건 **최종 목표의 서술이지 지금 구현하라는 허가가 아니다**라고 명시 (한국어 `구현`, `구현 계획`까지 문자열로 하드코딩).

```
deep-interview          ralplan consensus         별도 승인
(명료성 게이트)   ──▶   (타당성 게이트)     ──▶   (동의 게이트)
spec.md                 consensus-plan.md         ultragoal / team
```

3단계인 이유가 문서에 명시돼 있다: ① 사용자가 뭘 원하는지 아는가 ② 접근이 아키텍처적으로 건전한가 ③ 사용자가 명시적으로 실행 경로를 선택했는가. **각각 다른 종류의 게이트.**

### 5.1 자기 남용 방지 게이트 (Phase 0.5)

Suitability Gate가 스킬 자신의 오용을 막는다. 파일 경로·함수명·수용 기준이 이미 있거나, 빠른 수정이거나, 브레인스토밍(→ ralplan)이거나, 이미 PRD가 있으면 **즉시 중단**한다. "그냥 해"는 pending spec을 쓰는 게 아니라 **인터뷰를 종료해서** 존중한다.

문서의 자기 규정: *"이 게이트는 deep-interview가 쉬운 문제를 어렵게 만드는 것을 막기 위해 존재한다. 약간의 확인 필요가 인터뷰 대상이 되는 것은 아니다."*

`[도출]` **무거운 워크플로 스킬은 자기 진입 거부 조항을 반드시 가져야 한다.** 우리 SKILL.md에도 필요하다.

## 6. 비판 — 축을 나눠도 채점하는 건 결국 LLM이다

### 6.1 채점 구조 `[gjc]`

모호함을 직접 재지 않고 명료함을 4축으로 분해해 각각 0~1로 재고 가중합의 여집합을 취한다.

```
그린필드:   ambiguity = 1 - (목표×0.40 + 제약×0.30 + 기준×0.30)
브라운필드: ambiguity = 1 - (목표×0.35 + 제약×0.25 + 기준×0.25 + 맥락×0.15)
```

각 축은 판정 가능한 질문으로 정의된다 — 특히 기준 축의 *"이 요구사항으로 테스트를 쓸 수 있나?"*.

### 6.2 그러나 이것은 HR 루브릭과 구조적으로 같다 `[도출]`

**축을 나눈다고 객관성이 생기지 않는다. 분해가 생길 뿐이다.** "조직융화성 3점"과 "제약 명료도 0.4"는 둘 다 누군가의 인상을 숫자로 적은 것이다.

HR 루브릭이 비판받는 세 이유가 그대로 있다:

| HR 루브릭의 문제 | deep-interview |
| --- | --- |
| 가중치에 근거 없음 | **있음.** 0.40/0.30/0.30의 출처가 코드·문서 어디에도 없음 |
| 가짜 정밀도 (0.7 vs 0.6) | **있음.** 소수점 첫째 자리는 사실상 노이즈 |
| 이미 내린 결론을 숫자로 정당화 | **있음.** 모델이 "끝내고 싶은" 상태면 점수도 그렇게 나옴 |

그리고 결정적으로 — **"모호도 51%"는 세상에 대한 어떤 검증 가능한 주장도 아니다.**

### 6.3 그럼에도 다른 점 3가지, 강한 순서로 `[도출]`

**① 점수가 아니라 argmin이 실제 작동부다 (가장 강함).**

HR 루브릭은 **점수가 곧 판결**이다. 3.7점 → 불합격, 복구 불가. 여기서 점수의 실제 용도는 **"다음에 뭘 물어볼까"** 하나뿐이다.

필요한 것은 **서수 정확도**뿐이다. "셋 중 기준이 제일 약한가"만 맞으면 되고 0.3이 정확히 0.3인지는 무관하다. 그리고 LLM은 **절대 교정은 형편없지만 같은 맥락 내 상대 비교는 잘한다.** 이 시스템은 잘하는 것만 쓰고 있다.

오류 비용도 비대칭이다. HR이 틀리면 잘못된 채용(복구 불가), 여기서 틀리면 **엉뚱한 질문 하나**(다음 라운드에 재채점).

**② floor는 진짜로 LLM이 안 매긴다 — 다만 범위가 좁다.**

§3.1의 세 항은 세면 나오는 정수다. HR로 치면 "면접관 인상"이 아니라 "필수 서류 2개 미제출"에 해당.

**단, 정직해야 한다:** 모순도 없고 모든 컴포넌트를 물어봤고 대리답변도 없으면 floor는 0이고, **그때부터는 LLM 점수가 유일한 문지기다.** floor는 점수를 객관화한 게 아니라 **객관적으로 잡을 수 있는 것만 따로 떼어낸 것**이다.

**③ 정성 판단과 정량 출력을 강제 결합한다.**

§3.3의 TRANSITION VALIDATION. 모델이 "3라운드와 모순됨"이라 써놓고 점수를 올리는 것이 형식적으로 금지된다. 트리거를 아예 보고 안 하면 뚫리지만, **그건 거짓말을 해야 뚫리는 것**이고 그냥 후하게 주는 것보다 문턱이 높다.

### 6.4 결론: 이것은 측정이 아니라 스케줄러다 `[도출]`

정직한 정체는 "요구사항의 모호도"가 아니라 **"다음 질문을 어디에 쓸지, 언제 패널을 부를지 정하는 우선순위 큐"**다.

증거: 패널 소집 기준이 점수가 아니라 **band**다.

```
initial   > 0.60
progress  0.60 ~ 0.30
refined   0.30 ~ threshold
ready     ≤ threshold
```

0.61과 0.59는 다르지만 0.61과 0.65는 같다. **소수점 정밀도를 애초에 신뢰하지 않는 설계.**

그리고 인터뷰의 실제 산출물은 점수가 아니다 — `established_facts`, SHA-256으로 봉인된 `intent_contract`, `topology`, `ontology_snapshots`, transcript 전문. **점수를 전부 지워도 spec은 만들어진다.**

## 7. 발견한 결함 — 기본 임계값 0.05는 도달 불가능하다 `[gjc]` `[도출]`

임계값 해석 순서:

| 조건 | threshold |
| --- | --- |
| 플래그 없음 (기본) | **0.05** |
| `--quick` | 0.6 |
| `--standard` | 0.5 |
| `--deep` | 0.35 |

0.05는 목표·제약·기준이 **전부 0.95 이상**이어야 나온다. LLM 채점으로 현실적으로 도달하기 어렵다.

그런데 종료 조건 목록에 우회로가 명시돼 있다:

> **모든 축이 0.9 이상**: 라운드 최소치를 안 채웠어도 spec 생성으로 건너뛴다

전 축 0.9면 모호도는 **0.10**으로, 임계값 0.05를 못 넘겼는데 통과시킨다. **수학적 게이트를 우회하는 경로가 설계에 내장돼 있다.**

여기에 조기 종료(3라운드+), 라운드 4~15의 "계속할까요?" 확인, 16+ 수익체감 경고, 100라운드 하드캡, Phase 4의 closure/restate 게이트를 합치면:

> `[도출]` **기본 설정에서 인터뷰를 실제로 종료시키는 것은 수학이 아니라 사람의 판단과 정성적 게이트다. 수학은 질문 순서를 정하는 데는 실제로 쓰이고, 종료 판정에서는 대체로 우회된다.**

이것이 기수 게이트의 **필연적 귀결**이다. 절대 수준에 대한 주장이 원래 불가능하기 때문에, 그 위에 세운 임계값은 도달 불가능하거나 임의적이거나 둘 중 하나가 된다.

## 8. 미시경제학 연결 — 같은 위기, 90년 간격 `[econ]` `[도출]`

### 8.1 1930년대의 문제

초기 효용 이론은 "사과 5 util, 배 3 util"이라 썼다. 문제는 **util을 재는 기계가 없다**는 것. 효용 이론 전체가 검증 불가능한가?

**첫 번째 해결 — 서수적 효용.** 사과=10/배=5든 사과=100/배=1이든 선택은 같다. 임의의 엄격 단조증가함수 `f`에 대해 `V = f(U)`는 동일한 선호 체계다. **의미 있는 것은 순서뿐이고 숫자는 라벨이다.**

**두 번째 해결 — 현시선호 (Samuelson).** 묻지 말고 관찰하라. 머릿속은 못 봐도 선택은 볼 수 있고, 선택은 선호를 드러낸다.

**핵심 조건 — 예산집합.** "커피를 샀다"는 정보가 아니다. **"차를 살 수 있었는데 커피를 샀다"**가 정보다. 차가 품절이거나 두 배 비쌌다면 아무것도 드러나지 않는다. 현시선호는 항상 **"그때 무엇을 고를 수 있었는가"와 짝으로만** 성립한다.

**WARP (약공리).** 같은 조건에서 선택이 뒤집히면 일관성 위반. 조건(가격)이 달라졌다면 위반이 아니다.

**이행성과 머니 펌프.** `짜장면 > 짬뽕 > 볶음밥 > 짜장면` 인 사람은 100원씩 얹어주는 교환을 무한히 반복당해 지갑이 빈다. **이행성은 "있으면 좋은 성질"이 아니라 없으면 착취당하는 조건이다.**

### 8.2 매핑

| 미시경제 `[econ]` | deep-interview `[gjc]` |
| --- | --- |
| 소비 묶음 x, y | (컴포넌트 × 축) 칸 — `Export.criteria` 등 |
| 효용 U(x) | 그 칸의 명료도. **관측 불가** |
| 관측된 선택 x^t | 라운드 t에서 모델이 고른 최약 칸 |
| 예산집합 | 그 라운드의 선택 가능 칸 집합 |
| 가격 변화 | **토폴로지 변화** (컴포넌트 추가/미룸, 브라운필드 축 개폐) |
| 새 재화의 등장 | **트리거 D (스코프 확장)** |
| 단조증가변환 불변성 | 0.40/0.30/0.30 가중치에 근거가 없어도 **순위만 보존되면 무관** |

**진단: 현재 설계는 Samuelson 이전 방식이다.** 모델에게 "몇 util이냐"고 묻고 그 대답을 받아 적는다.

### 8.3 버려지고 있는 데이터 `[도출]`

라운드마다 모델은 argmin 하나를 고르지만, 그것은 사실 **"이 칸이 나머지 n-1개 전부보다 약하다"**는 n-1개의 비교다. 칸이 12개면 라운드당 11개의 순서 관측치.

현재 시스템은 이를 `weakest_dimension` 문자열 하나로 납작하게 만들고 버린다. 10라운드면 100개 넘는 비교가 생기는데 **아무 데도 안 쌓이고 아무 공리도 안 걸린다.**

### 8.4 예산집합의 정체 — 증거 상태 `[도출]`

순수 WARP를 그대로 걸 수 없다. 소비자 선호는 관측 기간 동안 고정이라 가정하지만, **여기서 명료도는 정당하게 변한다** (사용자가 답하면 진짜로 명확해진다).

해법: **증거 상태(evidence state)로 조건을 건다.**

```
라운드 3: Export ≺ ReviewUI  (Export가 덜 명확)
라운드 4: 사용자가 Export의 기준에 대해 답함      ← 조건 변화 = 가격 변화
라운드 5: ReviewUI ≺ Export                      ← 정상. 위반 아님
```

```
라운드 3: Export ≺ ReviewUI
라운드 4: 사용자가 Normalization만 답함           ← 둘 다 안 건드림
라운드 5: ReviewUI ≺ Export                      ← WARP 위반
```

같은 증거 상태 = 같은 예산집합. 그 안에서의 뒤집힘만 위반으로 센다. 상태에 이미 `last_targeted_component_id`와 라운드별 `affected_component`가 있으므로 **현행 스키마로 계산 가능하다.**

## 9. 적용안 — 구현 난이도 순 `[도출]`

### 9.1 (A) 기수 버리고 비교 그래프를 1급 시민으로

라운드마다 점수 대신:

```json
{
  "ranking": ["Export.criteria", "Normalization.goal", "Export.goal"],
  "ties": [["Export.goal", "ReviewUI.constraints"]],
  "evidence_state_id": "sha256:...",
  "note": "Export.criteria는 '감사 가능'의 판정 기준이 전무"
}
```

argmin 하나 대신 **약한 순 상위 3~5개**를 뽑게 하면 엣지가 몇 배로 늘고 비용은 거의 같다. 표시용 숫자가 필요하면 Bradley-Terry / Elo로 **사후 복원**한다 — 숫자가 입력이 아니라 파생물이 된다.

### 9.2 (B) WARP 위반 카운트 = 결정론적 드리프트 탐지 ★

**가장 값어치 있는 적용.**

floor가 애초에 만들어진 이유가 "LLM이 anchoring해서 드리프트한다"였는데, 현재 방식은 드리프트의 **부작용**(모순 사실 축적)을 세는 간접 관측이다. WARP 위반은 **드리프트 자체를 직접, 절대 교정 없이** 관측한다.

- ✗ "Export가 0.3인가?" → 검증 불가, 의견
- ✓ "같은 증거 상태에서 순서가 뒤집혔나?" → **검증 가능, 기록 대조로 판정**

**평가의 내용은 감사할 수 없지만 평가의 일관성은 감사할 수 있다.** §6.2의 HR 루브릭 비판에 대한 유일한 실질적 반격 지점이다.

floor 확장:

```
floor += 0.05 × (증거 상태 불변 구간 내 WARP 위반 건수)
```

§3.2에서 본 이식 단위(공백 / 모순 / 증거희석)에 **네 번째 축(일관성)**을 추가하는 셈이다.

### 9.3 (C) 사이클 = 질문 머니 펌프

`A ≺ B ≺ C ≺ A`는 **어떤 명료도 함수로도 합리화 불가능**하다. 모델이 수렴 중이 아니라 진동 중이라는 뜻이고, 결과는 질문의 무한 순환 — 털리는 것이 돈이 아니라 **사용자의 주의력**이라는 것만 다르다.

현행 stall 탐지("3라운드 연속 ±0.05")는 못 믿을 숫자로 못 믿을 숫자를 재는 것이라 약하다. 대안:

```
incoherence = 최소 피드백 아크 집합의 크기
            (그래프를 비순환으로 만들려면 최소 몇 개 엣지를 제거해야 하는가)
```

순수 조합론이고, 노드가 최대 6×4=24개라 근사로 충분하다. 존재론 리프레임의 훨씬 나은 방아쇠.

### 9.4 (D) 게이트를 수준에서 순위 안정성으로 ★

§7의 결함(임계값 0.05 도달 불가 + 우회로 내장)에 대한 근본 처방.

> **수렴 = 순위 안정 + 사이클 0 + 모든 active 컴포넌트가 최소 1회 최약체로 지목됨**

1. active 컴포넌트 명료도 순위가 최근 k 라운드 불변 (Kendall tau = 1)
2. 사이클 0개
3. 전 컴포넌트가 최소 1회 argmin 경험 — **한 번도 최약체가 못 된 컴포넌트 = 한 번도 진지하게 다뤄지지 않은 컴포넌트.** 현행 `0.05 × 미채점` 항의 서수 강화판

- ✗ "요구사항이 5% 모호합니다" → 검증 불가
- ✓ "질문을 더 해도 우선순위가 안 바뀝니다" → **관측된 사실**

**임계값 튜닝이 사라진다.** 0.05냐 0.35냐를 다툴 일이 없다.

### 9.5 설계가 이미 답의 절반을 갖고 있다 `[도출]`

§4.2의 `stability_ratio`가 **정확히 서수적 수렴 지표**다. 엔티티 집합의 안정성만 재고 품질 점수를 매기지 않으며 절대 척도 주장이 없다.

그런데 이것은 **진단 정보로만 표시되고 게이트로는 안 쓰인다.** 게이트는 여전히 기수다.

> **(D)는 새 발명이 아니라 "이미 옳게 만들어놓은 것을 게이트로 승격시켜라"이다.**

## 10. 방증과 한계

### 10.1 RLHF — 이미 승리한 패러다임 `[도출]`

RLHF의 보상 모델은 **절대 점수가 아니라 선호 쌍으로 훈련된다.** 이유가 동일하다 — 사람은 "7.3점"을 일관되게 못 매기지만 "A가 낫다"는 잘 한다. 쌍 비교에서 스칼라를 복원하는 Bradley-Terry는 사실상 현시선호의 통계 버전이다.

> **LLM을 훈련시킬 때는 절대 점수를 안 믿으면서, 그 LLM을 하네스 안에서 굴릴 때는 자기 절대 점수를 믿는다.**

이것은 비유의 문제가 아니라 **일관성의 문제**다.

### 10.2 한계 3가지 — 공짜 점심은 없다 `[도출]`

**① 조건 변화 판정의 애매함.** Export에 대한 답변이 ReviewUI의 명료도에도 영향을 줄 수 있다. 어떤 엣지가 아직 유효한지 판정하는 규칙이 필요하고, 보수적이면 데이터가 안 쌓이고 공격적이면 거짓 위반이 생긴다. **기수 임계값(0.05)을 없앤 자리에 다른 임의성이 들어온다.**

**② 완비성 불성립.** 종류가 너무 다른 칸은 LLM이 진짜로 비교 못 할 수 있다. 억지 순서 강제는 노이즈 공장이 된다. → GARP가 평평한 무차별 구간을 허용하듯 **명시적 "≈" 엣지를 허용해야 한다.**

**③ 개인간 비교 불가 = 인터뷰간 비교 불가.** 순위는 한 인터뷰 안에서만 유효하다. "이 spec이 저 spec보다 명확하다"를 말할 수 없다.

다만 현재 설계는 0.05라는 절대 기준으로 그것이 되는 **척**하고 있고, 그건 원래 불가능한 주장이다. **서수 버전은 잃는 것이 아니라 그 거짓말을 정직하게 포기하는 것이다.** 대신 조직 단위 대시보드("팀 평균 명료도")는 불가능해진다.

## 11. 이 프로젝트에 무엇을 가져갈 것인가 `[도출]`

### 11.1 채점 대상 매핑

| 대상 | 기수 방식 (gjc 현행) | 서수 방식 (제안) |
| --- | --- | --- |
| 유스케이스 커버리지 | "커버리지 0.7" | 유스케이스를 **미명세 순으로 정렬**, 순위 안정까지 |
| 요구사항 우선순위 | "중요도 8점" | 쌍 비교 + WARP 검사 (P0/P1 라벨 인플레의 근본 처방) |
| spec 완성도 게이트 | 점수 임계값 | **순위 불변 k 라운드 + 사이클 0 + 전 항목 1회 지목** |
| 모델 드리프트 감사 | 없음 | **증거 불변 구간 내 순위 뒤집힘 카운트** |

### 11.2 하네스 3층 배분 갱신

자매 문서 [`skill-vs-harness`](./2026-08-19-skill-vs-harness.md) §7.2의 배분표에 이 문서의 결론을 더하면:

| 층 | 추가되는 것 |
| --- | --- |
| **하네스** | 비교 그래프의 단일 정본 writer · 증거 상태 해시 발급 · 순위 안정성 게이트 |
| **스크립트** | **WARP 위반 검출 · 사이클/피드백아크 계산 · Kendall tau 안정성 · 전 항목 지목 커버리지** |
| **SKILL.md** | 무엇을 "독립 컴포넌트"로 볼지 · 비교 불가("≈")를 언제 선언할지 · 존재론 리프레임 판단 |

`[도출]` **WARP/SARP 검사는 완벽하게 결정론적이면서 LLM 판단의 품질을 감사한다.** LLM 판단이 하나도 안 들어가는데 LLM 판단을 검증한다는 점에서, 자매 문서가 말한 "백테스터에 해당하는 것"의 두 번째 후보다. 첫 번째는 추적성/전파 검증기.

### 11.3 즉시 적용할 규칙

1. **모델에게 절대 점수를 요구하지 않는다.** 필요하면 순위를 받고 숫자는 사후 복원한다.
2. **모든 비교 판정에 증거 상태 해시를 붙여 저장한다.** 이것이 없으면 나중에 어떤 일관성 검사도 못 한다. **스키마 설계 시점에 넣어야 하는 필드다.**
3. **게이트는 수준이 아니라 안정성으로 건다.** "충분히 명확한가"가 아니라 "더 물어도 순서가 안 바뀌는가".
4. **`floor`의 네 축을 그대로 이식한다** — 공백 / 모순 / 증거희석 / **일관성**. 필드가 아니라 축을 옮긴다.
5. **자기 진입 거부 조항을 SKILL.md에 넣는다** (§5.1). 무거운 워크플로는 자기 남용 방지가 필수다.

자매 문서 [`ralplan 해부`](./2026-08-28-ralplan-consensus-harness-and-reviewer-sandbox.md) §9.3에서 두 개가 더해진다:

6. **강제 3단계를 의식적으로 배치한다.** 강제할 수 있으면 코드로, 못 하면 최소한 **프롬프트 + 존재 회귀 테스트**로. 그냥 산문에 남기는 것은 "언젠가 사라져도 좋다"는 선언이다. 이전 노트의 하네스/스킬 이분법을 3단계로 갱신한다 — ① 강제 · ② **테스트된 산문** · ③ 그냥 산문.
7. **모델의 판단은 최신값이 아니라 시퀀스로 저장한다.** 규칙 2의 일반화이며, **두 하네스에서 연속으로 확인된 실패 패턴**이다 (아래 §11.5).

### 11.4 다음 단계 — 의견 싸움을 측정으로

전면 교체 대신 **(B) 하나만** 먼저:

> 현행 기수 채점을 그대로 두고, 라운드마다 "약한 순 3개"를 추가로 뱉게 한 뒤, **증거 불변 구간 내 뒤집힘 횟수만 로그에 남긴다.** 아무것도 차단하지 않는다.

```
인터뷰 12건 / 총 87라운드 / 증거 불변 구간 내 순서 뒤집힘: N건
```

**이 N이 곧 "지금 쓰는 소수점 점수를 얼마나 믿어도 되는가"의 실측치다.** 0에 가까우면 기수를 유지해도 되고, 크면 (D)로 갈 근거가 데이터로 확보된다. 설계 논쟁을 계측으로 치환하는 것이 이 아이디어의 실질적 값어치다.

### 11.5 후속 확인 — 같은 실수가 ralplan에서 재발한다 `[도출]`

[`ralplan 해부`](./2026-08-28-ralplan-consensus-harness-and-reviewer-sandbox.md) §7에서 확인된 사실이 이 문서의 §8.3(버려지고 있는 데이터)을 일반화한다.

ralplan은 이 문서의 비판을 **애초에 피해 간다** — 기수 점수를 쓰지 않고 3단계 서수 토큰(`CLEAR`/`WATCH`/`BLOCK`, `OKAY`/`ITERATE`/`REJECT`)만 쓴다. 그런데 그 서수의 **이력을 버린다**:

| | 수집하는 것 | 저장하는 것 | 잃는 것 |
| --- | --- | --- | --- |
| deep-interview | 라운드마다 n-1개의 비교 엣지 | `weakest_dimension` 문자열 1개 | 비교 그래프 → WARP 검사 불가 |
| ralplan | 패스마다 레인별 평결 | `last_review_verdict` 슬롯 1개 (덮어씀) | 평결 시퀀스 → 단조성 검사 불가 |

특히 ralplan의 ratchet **Rule 3 (verdict monotonicity)** — *"이전 패스의 blocker가 전부 해소되면 평결은 나빠질 수 없다"* — 는 **WARP와 같은 형태의 일관성 공리**다. 조건이 같으면 판정이 뒤집히면 안 된다는 것. 그리고 CLI가 `--lane-verdict`로 모든 평결을 이미 받고 있는데도, 영구 원장(`index.jsonl`) 행에는 평결이 들어가지 않아 **검사에 필요한 데이터가 남지 않는다.**

`[도출]` **§9.2(WARP 위반 카운트)는 deep-interview 전용 처방이 아니라 두 하네스 공통의 처방이다.** 서수적 판단을 수집하는 모든 지점에서 시퀀스를 보존하고 일관성 공리를 코드로 검사하는 것 — 이것이 §11.3 규칙 7로 승격된 이유다.
