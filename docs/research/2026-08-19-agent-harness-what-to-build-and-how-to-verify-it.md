# 에이전트 하네스: 무엇을 만들고, 어떻게 검증하는가

- 작성일: 2026-08-19
- 분석 대상: `references/deepseek-harness` (`dsh-v0.1.0-rc.7`), `references/gajae-code` (`v0.13.2`)
- 성격: 연구 노트. 결정이 아니라 설계 판단의 근거를 모은 것이다. 확정된 제품 결정은 [`docs/prd.md`](../prd.md)에 있다.

## 0. 출처 표기

| 표기 | 뜻 |
| --- | --- |
| `[dsh]` | deepseek-harness 스냅샷에서 직접 확인한 규칙 또는 코드 |
| `[gjc]` | gajae-code 스냅샷에서 직접 확인한 규칙 또는 코드 |
| `[도출]` | 위 두 레포의 관찰로부터 이 프로젝트를 위해 도출한 것 |

두 레포는 상류를 추적하지 않는 정지 스냅샷이다([`references/FROZEN.md`](../../references/FROZEN.md)).

## 1. 중심 명제

> 하네스는 모델의 **능력(capability)** 을 보완하는 것이 아니라, 모델의 **구조적 한계(structure)** 를 보완하는 것이다.

능력 부족은 시간이 해결한다. 구조적 한계는 모델이 아무리 좋아져도 그대로다. 이 문서의 나머지는 전부 이 구분에서 파생된다.

| | 능력 부족 | 구조적 한계 |
| --- | --- | --- |
| 뜻 | 지금은 잘 못함 | 원리적으로 못함 |
| 예 | "좋은 use case를 못 씀" | "어제 뭘 결정했는지 기억 못 함" |
| 시간이 지나면 | 해결됨 | 그대로 |
| 하네스에 넣으면 | 나중에 짐이 됨 | 영구 자산 |

## 2. 핵심 통찰 열 가지

1. **모델이 원리적으로 못 하는 것은 여섯 가지뿐이다.** 기억 · 재현 · 권한 · 세상 확인 · 자기 채점 · 완전성 보장. 하네스의 영구 지분은 정확히 이것이고, 나머지는 시한부다. `[도출]`
2. **workflow(순서 강제)는 가장 먼저 흡수되는 부분이다.** "하네스 = 워크플로를 짜는 것"이라는 전제가 함정이다. 좋은 모델은 순서를 알아서 지키고, 그때 강제된 순서는 족쇄가 된다. 남는 것은 순서가 아니라 상태와 불변식이다. `[도출]`
3. **강제되는 것은 런타임에, 흡수될 것은 프롬프트에 둔다.** dsh는 guard 패키지에서 `advisory`와 `enforcer`를 나눠 부르고, gjc의 ralplan은 게이트를 전부 CLI에 넣고 리뷰 규율은 마크다운에 남겼다. 서로 모르는 두 코드베이스에서 같은 선이 독립적으로 그어졌다. `[dsh]` `[gjc]`
4. **부기(簿記)가 유일하게 비어 있는 자리다.** 가치 판단은 사람 몫이고 발산·작문은 이미 흔하다. 추적성 유지 · 변경 영향 파악 · 결정 이유 보존만 남는다. `[도출]`
5. **만들 것은 문서 생성기가 아니라 설계용 CI다.** 코드에는 테스트 스위트가 있어 바꾸면 무엇이 깨졌는지 알려주지만, 설계 문서에는 그게 없어서 썩는다. 최고 효용은 변경 영향 전파다. `[도출]`
6. **추론시키지 말고 관측시켜라.** ruff는 AST를 파싱하고 pytest는 코드를 실행한다. 둘 다 추론하지 않아서 싸고 결정론적이다. `[도출]`
7. **자기 보고가 아니라 세상을 검증하라.** 출력에 키워드가 있는지 보는 검증은 커닝하는 에이전트를 통과시킨다. `[dsh]`
8. **테스트의 근거는 상상이 아니라 실험이다.** 실제 데이터로 돌린 PoC의 결과가 오라클이다. 오라클은 발명하는 게 아니라 수확하는 것이다. `[도출]`
9. **에이전트의 무기억증은 무한한 신선한 초심자다.** 사람은 한 번 쓰면 더 이상 처음이 아니지만 에이전트는 매번 처음이다. 최대 약점이 최고의 실험 장비가 된다. `[도출]`
10. **에이전트가 사용자라면 시뮬레이션이 곧 모집단이다.** "그래서 인간한테도 통해?"라는 질문이 적용되지 않는다. 외적 타당도 격차가 없다. `[도출]`

## 3. 판정: 무엇이 하네스가 되고 무엇이 안 되는가

### 3.1 모델의 여섯 가지 구조적 한계 `[도출]`

모델은 아무리 좋아져도 텍스트가 들어가면 텍스트가 나오는, 한 번의 호출로 끝나는, 확률적인 함수다.

| 한계 | 왜 원리적인가 | 하네스의 몫 |
| --- | --- | --- |
| 기억 | 컨텍스트가 1억 토큰이어도 다음 세션엔 없다 | 로그, 그래프, 결정 이력 |
| 재현 | 확률적이라 같은 질문에 다른 답이 나온다 | 검증기, 게이트, 링크 체크 |
| 권한 | 파일 쓰기도 승인 받기도 하네스가 허락해야 일어난다 | 툴, 승인 흐름 |
| 세상 확인 | "파일을 썼습니다"와 "파일이 써졌다"는 다르다 | 외부 관측, 재실행 |
| 자기 채점 | 채점자와 응시자가 같으면 똑똑함과 무관하게 무의미 | 모델 바깥의 판정 경로 |
| 완전성 | "다 찾았다"는 열거로만 보장되고, 열거는 기계의 일 | 전수 순회, 영향 전파 |
| (+ 자기 정지) | 스스로 멈추지 못한다 | 예산, 반복 한도 |

### 3.2 리트머스 두 장 `[도출]`

- **Test A** — "모델이 10배 똑똑해지면 이 기능이 필요 없어지는가?" 예면 얇게 만들고 뜯어내기 쉽게, 아니오면 단단히.
- **Test B** — "이건 모델을 *돕는* 것인가, 모델을 *기억하고·제약하고·관찰하는* 것인가?" 돕는 것은 흡수되고, 기억·제약·관찰·열거는 남는다. **하네스의 영구 지분은 전부 비(非)인지적이다.**

### 3.3 플러그인 판정 3문항 `[dsh]`

1. 프로젝트/배포마다 실제로 다른 값을 갖는가? 아니오면 상수다. `DEFAULT_*` 상수를 두고 "나중에 고치지 뭐"는 설정 가능성이 아니다.
2. 구현이 지금 둘 이상 있거나 곧 생길 것이 확실한가? 아니오면 seam을 만들지 않는다.
3. 이걸 바꿔서 산출물을 믿을 수 없게 만들 수 있는가? 예면 고정한다. 1번이 "예"였어도 이것이 이긴다.

dsh의 원문 규칙은 대칭이다 — *배포마다 달라지는 선택은 검증된 `Config` 필드로 만들고, 프로토콜 상수·외부 규격·보안 불변식은 고정한다.* **빼야 할 것을 안 뺀 것도 위반이고, 빼면 안 될 것을 뺀 것도 위반이다.** 유연성은 미덕이 아니라 판단 대상이다.

### 3.4 advisory / enforcer 라벨링 `[dsh]` `[gjc]`

| 라벨 | 성격 | 예 | 판정 |
| --- | --- | --- | --- |
| `advisory` | 모델에게 알려만 준다 | 반복 호출 알림, 형식 가이드, 역할 프롬프트 | 흡수될 것 |
| `enforcer` | 진짜로 막는다 | 데드라인, 반복 한도, 승인 게이트, 변경 차단 | 영구 |

모든 기능에 이 라벨을 붙여 두면, "모델이 좋아졌으니 무엇을 뺄까?"의 답이 목록으로 이미 나와 있다.

## 4. 구성: 어떻게 조립하는가

### 4.1 흡수될 것은 플러그인으로, 영구한 것은 코어로 `[도출]`

흡수될 기능을 만들지 *말라*는 뜻이 아니다. 지금은 실제로 도움이 된다. 문제는 그것을 코어 깊숙이 박아 넣는 것이다.

### 4.2 capability seam: 세 역할 `[dsh]`

| 역할 | 비유 |
| --- | --- |
| Service Definition | 콘센트 규격 |
| Service Provider | 실제 발전소 |
| Consumer (흔히 모델용 툴) | 가전 |

세 역할이 다 있어야 seam이다. 실익은 명확하다 — 파일시스템과 프로세스 실행의 구현체만 원격 샌드박스로 바꾸면 Bash·터미널·LSP가 통째로 따라 옮겨간다.

같은 규칙에 제동장치가 붙어 있다: **"역할이 독립적으로 진화할 때만 쪼개라."** 구현이 하나뿐이고 앞으로도 하나뿐일 것 같으면 콘센트를 만들지 않는다. "언젠가 바꿀지도"는 근거가 아니다.

### 4.3 마찰을 일부러 넣기 `[dsh]`

*"플러그인으로 하라, 루프를 고치지 말라. `agent-loop`를 바꾸려면 아키텍처 문서를 갱신해야 한다."* 루프도 교체 가능한 한 줄이지만, 바꾸려면 통행료를 내게 만들었다. 쉬운 길과 어려운 길을 설계한 것이다.

### 4.4 구성은 설정으로 외재화 `[dsh]`

프로필 → 번들 → 패치 레이어. 무엇으로 만들어질지가 코드가 아니라 YAML에 있고, `dsh --profile web --dump-config`가 실제로 부팅된 트리를 출력한다. 거기 찍힌 모든 행이 id로 패치 가능하다는 것이 검증 수단이다.

## 5. 검증: 어떻게 믿는가

| 원칙 | 내용 | 출처 |
| --- | --- | --- |
| 세상을 검증 | 명령을 다시 실행하고 파일을 바깥에서 다시 읽는다. 손대지 않은 파일이 바이트 단위로 같은지도 본다 | `[dsh]` |
| 가드는 회귀로 검증 | 일부러 회귀를 도입하고, 빨간불을 확인하고, 되돌린다. 안 그러면 아무것도 못 잡는 채로 늘 초록불이다 | `[dsh]` |
| 가짜보다 진짜 | 비싸거나 비결정적인 경계(LLM·네트워크·시계)만 mock하고 그 아래는 전부 진짜. 배포되는 산출물을 실제 진입 경로로 실행 | `[dsh]` |
| 커버리지의 해석 | "라인 커버리지는 필요조건이지 충분조건이 아니다." 그리고 안 덮인 줄은 대개 붙일 테스트가 아니라 지울 죽은 코드다 | `[dsh]` |
| 런타임 불변식 | 테스트가 아니라 실행 중에 도는 검사. 메서드 존재 확인은 불변식이 아니고 관찰 가능한 이벤트·데이터 관계만 해당된다 | `[dsh]` |
| 침묵 금지 | 검사할 게 없으면 `No runtime invariant: <이유>`를 쓰게 강제하고, 이유 없는 빈 것은 게이트가 거부한다 | `[dsh]` |
| 방어의 위치 | 타입 있는 같은 프로세스 경계에서는 타입을 믿는다. 검증은 parser/config · 큐 · 모델 JSON · 파일 · 워커 · 프로세스 · 와이어에서만 | `[dsh]` |
| 출처 대조 | 리뷰가 정확히 그 버전에 대한 것임을 `sha256`으로 증명. 출처가 위조·불일치면 쓰기 자체를 거부한다 | `[gjc]` |
| 충돌 강제 처분 | 두 리뷰어가 같은 대상에 양립 불가능한 조치를 지시하면, 명시적 처분이 기록될 때까지 진행 불가 | `[gjc]` |
| 영수증만 반환 | 역할 에이전트는 본문을 반환하지 않고 `path`·`sha256`·판정만. 컨텍스트 절약과 위변조 방지를 동시에 | `[gjc]` |

### 5.1 내부 결함의 세 탐지기 `[도출]`

| 결함 | 정의 | 탐지기 |
| --- | --- | --- |
| 보일러플레이트 | 어떤 쇼케이스도 **도달하지 못하는** 코드 | 도달성(coverage) |
| 구멍(hole) | 쇼케이스가 **지나가지만 확인하지 않는** 것 | 뮤테이션 생존자 |
| 투기적 API | 어떤 쇼케이스도 **쓰지 않는** public export | export ↔ 사용처 대조 |

뮤테이션 테스팅이 실무에서 안 쓰이는 이유는 살아남은 뮤턴트를 사람이 일일이 분류해야 해서다. 그게 에이전트가 잘하는 일이다. 비싼 계산은 기계가, 지루한 분류는 에이전트가, 판단은 사람이 한다.

### 5.2 정직해야 할 지점 `[도출]`

추적성 100%는 좋은 설계의 필요조건이지 충분조건이 아니다. 완벽하게 추적 가능한 쓰레기 설계가 얼마든지 가능하다. **기계적 건전성만 게이트로 강제하고, 제품적 타당성은 사람에게 남긴다.**

## 6. 관측: 어떻게 보는가

에이전트가 "이 코드가 어떻게 동작해?"에 자주 틀리는 것은 능력 문제가 아니라 **정적 읽기 + 추론**이라는 방법의 문제다. 손실적이고(동적 디스패치·DI·설정 배선은 안 보임), 무한정이고(확신하려면 전부 읽어야 함), 확률적이다.

dsh 자신이 이 문제를 가장 심하게 겪는다. 모든 게 `ctx.<key>` 뒤에 있어 정적 읽기가 콘센트에서 끊긴다. 그래서 `--dump-config`와 생성된 카탈로그들을 CI freshness gate와 함께 만들었다. **문서가 아니라 계측 장비다.** `[dsh]`

### 6.1 계측기 하나, 산출물 넷 `[도출]`

```text
            격리 실행 + 계측 레이어
       (트레이스 + 행동 신호 기록)
                    │
   ┌─────────┬──────┼──────┬──────────┐
   ▼         ▼      ▼      ▼          ▼
 도달성   trace질의  pain   실험결과  trace diff
(죽은코드) (구조이해) point (A/B/decoy) (변경영향)
```

하나만 잘 만들면 넷이 딸려온다. 그리고 이 레이어가 정확히 영구 지분이다 — 관측 · 기억 · 열거 · 재현.

### 6.2 질의 가능해야 한다 `[도출]`

트레이스를 통째로 컨텍스트에 부으면 원래 문제를 그대로 재현한다. ruff가 좋은 건 결과가 짧고 정확해서지 AST를 다 보여줘서가 아니다.

```text
trace path      --from load_csv --to write_output
trace stack     --scenario showcase_01
trace shape     --at normalize
trace unreached --all-scenarios
trace diff      --before HEAD~1 --after HEAD
```

`trace diff`가 가장 저평가되어 있다. git diff는 텍스트 변화를, trace diff는 실행 구조 변화를 보여준다. "3줄 고쳤는데 왜 이렇게 됐지?"에 대한 결정론적 답이다.

### 6.3 static ∖ dynamic = 의심 구역 `[도출]`

| | 뜻 |
| --- | --- |
| 정적 (import 그래프, AST) | 일어날 수 있는 것 (상위집합) |
| 동적 (트레이스) | 실제로 일어난 것 (부분집합) |
| 차집합 | **이것이 산출물** — 죽었거나 검증 안 됐거나, 둘 다 조치가 필요 |

### 6.4 디버거는 이미 있다, 형태가 문제였다

VSCode 디버거는 DAP 클라이언트일 뿐이고 그 자리에 에이전트를 앉히면 된다. gjc가 이미 14개 언어 어댑터로 구현해 두었다(Python은 `debugpy`, `justMyCode: false`). `[gjc]`

다만 step 기반을 그대로 주면 안 된다. `frame_id`/`scope_id`/`variable_ref` 핸들을 에이전트가 들고 다녀야 하고, 변수 하나 보는 데 왕복 3회, 100줄 추적에 툴콜 100번이다. DAP는 인간의 IDE UI를 위한 프로토콜이다. `[도출]`

답은 **logpoint** — DAP에 이미 있는 `logMessage` + `condition`. 멈추지 않고 로그만 찍는 비대화형 프로브다. 한 번 심고, 한 번 돌리고, 표 하나를 읽는다.

| 단계 | 도구 | 언제 |
| --- | --- | --- |
| 1 · 배치 | 미리 뽑아 둔 트레이스 아티팩트 질의 | 기본값. 거의 항상 여기서 끝나야 한다 |
| 2 · 표적 | logpoint 프로브 | 배치에 없는 값이 궁금할 때 |
| 3 · 대화형 | 진짜 DAP 스텝 세션 | 원인 불명 진단. 최후 수단 |

Python 생태계에서 실제로 쓸 조합: `sys.monitoring`(PEP 669, 3.12+, 수집) + `coverage.py --context`(도달성) + `viztracer`(콜 그래프) + `MonkeyType`(형태 수확) + `debugpy`(프로브) + `py-spy`(현장 진단) + `sys.audit`(부작용 관측).

### 6.5 아키텍처 문서는 생성물이다 `[dsh]`

트레이스가 ground truth라면 다이어그램은 파생 뷰다. dsh의 `capability-seams.md` 첫 줄은 *"Generated — do not edit by hand"*이고 CI가 최신인지 검사한다. **"아키텍처 문서가 실제와 다르다"가 구조적으로 불가능해진다.**

## 7. 증거: 어떻게 안 썩게 하는가

실험 drift, 쇼케이스의 범위 한계, public interface 설계, TDD의 근거 — 네 문제가 전부 **주장(claim)의 출처와 유효기간** 하나다. `[도출]`

### 7.1 실험은 문서가 아니라 재실행 가능한 주장

```yaml
claim:        "10만 행 스트리밍 파싱 시 메모리 200MB 이하"
evidence:     {data: fixtures/sample-100k.csv, result: {peak_mb: 173}, at_commit: a3f9c2b}
depends_on:   [src/parser/stream.ts, src/io/chunk.ts]   # 바뀌면 STALE
falsified_if: "peak_mb > 200"                           # 기계적 판정
expires:      2026-11-01                                # 강제 결판
status:       PENDING | PROMOTED | FALSIFIED | EXPIRED
```

**누적을 막는 규칙**: 실험은 세 종착 상태 중 하나에 반드시 도달하며 `PENDING`으로 영원히 남을 수 없다.

- `PROMOTED` — 테스트가 됨. 이제 CI가 지킨다
- `FALSIFIED` — 삭제한다. 단 "왜 틀렸는지" 한 줄은 남긴다 (음성 결과도 자산)
- `EXPIRED` — 삭제한다

실험이 쌓여 무거워진다는 것은 삭제 경로가 없다는 뜻이다. **삭제를 기본값으로 만든다.**

### 7.2 승격 파이프라인 — TDD의 근거 문제가 여기서 풀린다

```text
실험     실제 데이터 → 실제 결과 (peak 173MB)
  ↓  승격 (기계적)
테스트    같은 데이터 → 200MB 이하인가?        ← 오라클이 실험에서 나옴
  ↓
쇼케이스  public interface로 같은 것을 재현
```

테스트에 "왜 이 값인가?"의 근거가 항상 붙어 있고, 승격되는 순간 CI 관할이 되어 drift가 멈춘다. **겪던 drift는 "실험 → 테스트" 경로가 없어서 생긴 것이다.** 실험과 테스트는 서로 다른 것이 아니라 같은 산출물의 다른 성숙 단계다.

### 7.3 같은 뼈대의 세 가지 적용

| 영역 | 그래프 | 전파 |
| --- | --- | --- |
| 제품 설계 | UC → 요구사항 → 컴포넌트 → 시나리오 결과 | 노드 변경 → 하류 STALE |
| 실험 | 주장 → 증거 → 의존 코드 | 코드 변경 → 주장 STALE |
| 랩 실험 | 가설 → arm → 결과 → 모델 버전 | 모델 변경 → 결과 STALE |

셋 다 **노드 · 엣지 · 출처 · 유효기간 · 전파**라는 같은 기계로 돈다. 매니페스트를 하나로 통합할지는 미해결이다(§10).

### 7.4 킬러 한 방: 그래프를 코드에 묶기

설계 문서가 항상 죽었던 이유는 유지할 이유가 없어서다. 컴포넌트 노드를 실제 파일 경로에 연결하면 양방향으로 썩음이 감지되고, 코딩 에이전트에게 설계 의도를 먹일 수 있는 유일한 기계가독 소스가 된다.

## 8. 발견: 어떻게 새 문제를 찾는가

### 8.1 Cold-start showcase `[도출]`

신선한 에이전트에게 public 타입 시그니처 + README + 과제만 주고, 레포 접근 · 소스 · 이전 대화 · 예제는 가린다. 성공했는지, 몇 번 만에, 어떤 에러에서 못 빠져나왔는지, 무엇을 잘못 짐작했는지를 측정한다.

이것은 **public interface에 대한 회귀 테스트**다. 인터페이스 설계가 감이 아니라 숫자가 된다. 부수 효과로 에러 메시지가 자동 등급화된다 — 에이전트가 회복하지 못한 에러는 코드 버그가 아니라 에러 메시지 버그다.

### 8.2 실패 원인을 넷으로 가른다

| 원인 | 제품 함의 | |
| --- | --- | --- |
| ① 기능이 없다 | 진짜 gap. 만들어라 | 기회 |
| ② 있는데 못 찾았다 | 발견성 — 이름·문서·introspection | 기회 |
| ③ 찾았는데 잘못 썼다 | API 설계 — affordance | 기회 |
| ④ 에이전트가 지금 약하다 | 흡수될 것. 만들지 마라 | 시한부 |

**④를 거르는 법: 모델 강도를 변주한다.** 약·강 모델 모두 실패하면 구조적(①②③)이고, 약한 모델만 실패하면 능력 문제(④)다. 싸고 결정적이며, 이 세팅에서만 가능하다 — "더 똑똑한 인간 사용자"는 주문할 수 없다.

측정할 행동 신호: 재시도 횟수, 썼다가 지운 코드(잘못된 길로 들어섰다가 돌아옴), 탐색 툴 폭주(발견성 실패), 에러 후 회복 실패(에러 메시지 버그), 잘못된 가정, 포기 지점.

### 8.3 agentic lab — 반사실이 관찰 가능해진다

인간 UX 연구에서 못 하는 네 가지가 여기선 전부 된다: 같은 피험자 반복, 사전 지식 완전 통제, 저렴한 대량 표본, 그리고 **같은 피험자의 treatment 없는 버전을 직접 관찰**.

**Decoy 설계가 성패를 가른다.** A에게 좋은 문서를 주고 B에게 아무것도 안 주면 A가 이긴다. 문제는 내용이 좋아서인지 컨텍스트가 더 많아서인지 구분이 안 된다는 것이다. decoy는 토큰 수와 형식이 일치하고 내용만 무관해야 한다. 그러면 효과가 분해된다.

```text
Decoy − Control     = 분량/형식 효과
Treatment − Decoy   = 실제 내용의 효과   ← 알고 싶은 것
```

이 분해 없는 A/B는 대부분 "토큰 더 줬더니 잘하네"의 재발견이다.

**타당성 위협 일곱**

| 위협 | 대응 |
| --- | --- |
| 사전학습 오염 (이미 그 라이브러리를 앎) | 심볼 개명, 새 도메인, "틀린 이름 프로브" |
| 비결정성 | arm당 n회 반복, 분포로 보고 |
| 판정자 오염 (LLM 채점) | 결정론적 결과 지표 우선 — 테스트 통과? 파일 일치? |
| 프롬프트 민감성 | arm마다 패러프레이즈 3~5개 |
| 모델 버전 drift | 모델 핀 고정 + provenance + 만료 |
| 다중비교 | 가설 사전등록. 20개 돌리면 무엇이든 "유의"해진다 |
| 생태학적 타당도 | **에이전트가 사용자면 해당 없음** — 시뮬레이션이 곧 모집단 |

### 8.4 "진짜 문제인가"는 물어보지 않는다

에이전트에게 판정을 맡기면 자기 채점이다. **문제가 진짜인지는 "제거해 봤을 때 결과가 달라지는가"로 답한다.** 그것이 개입 실험이다.

## 9. 이 프로젝트로의 적용

### 9.1 제품 스펙 하네스 (현 PRD)

| PRD 위치 | 내용 | 판정 |
| --- | --- | --- |
| §6 Phase 1~7 | 정해진 단계 순서 | 흡수 |
| §7 4역할 분리 | Explorer / Architect / Critic | 흡수 |
| §7 — Critic만 | "채점자가 응시자와 달라야 한다"는 구조 | **영구** |
| §8 산출물 계약 | 그래프 · 노드 · 엣지 · 영속 | **영구** |
| §8 | `APPROVED`는 사용자만 부여 | **영구** |
| §9 품질 게이트 | 전수 검사, 고아 탐지, 회귀 검토 | **영구** |
| §10 | Durable artifacts · Single canonical writer | **영구** |

§6·§7에 쓴 정성을 §8·§9로 옮겨야 한다. 현 문서는 워크플로 서술이 가장 두꺼운데 가치는 반대로 분포해 있다.

gjc의 `ralplan`에서 바로 가져올 것 넷 `[gjc]`:

1. **sha256 provenance** — 리뷰/판정이 정확히 그 버전의 산출물에 대한 것임을 증명
2. **join gate** — 한쪽 관점만으로 상태를 진전시키지 못하게
3. **강제 처분** — 충돌을 조용히 병합하는 것을 물리적으로 차단
4. **런타임 강제 반복 한도 + 명시적 STUCK 종결 상태** — 현 PRD의 종료 상태 목록에 "합의 실패"를 표현할 상태가 없다. `BLOCKED_BY_EVIDENCE`는 다른 뜻이다

### 9.2 에이전트가 1급 사용자인 라이브러리

| 인간 사용자 | 에이전트 사용자 | 설계 귀결 |
| --- | --- | --- |
| 한 번 배우고 기억함 | 매번 처음 | 학습이 아니라 호출 시점 발견 |
| 블로그·SO·동료에게 물음 | 타입과 docstring이 전부 | 부족(tribal) 지식 금지 |
| 막히면 검색 | 에러가 유일한 힌트 | **에러가 1차 문서 표면** |
| 이상하면 눈치챔 | 그럴듯하면 그냥 함 | 잘못된 상태를 표현 불가능하게 |
| 편의 오버로드 환영 | 오버로드 = 모호함 + 토큰 | 한 가지 명백한 방법만 |
| 40개 중 3개만 봄 | 40개를 다 읽음 | API 표면 = **컨텍스트 예산** |
| 사람에게 물어봄 | 혼자 확인해야 함 | **`verify()`가 1급 개념** |

dsh는 이미 이것을 레포 게이트로 강제한다 `[dsh]`. 모든 패키지 README에 `## Model Experience` 섹션("모델이 무엇을 보는가")이 없으면 `verify-package-readme-model-experience.ts`가 실패시키고, 카탈로그 생성기는 "모델이 행동할 수 없는 항목"이 있으면 빌드를 깨뜨린다.

## 10. 참조 구현 대조

| | deepseek-harness | gajae-code |
| --- | --- | --- |
| 정체 | 에이전트를 **만드는 틀** | 바로 쓰는 **완성 제품** |
| 심장(루프) | 목록의 한 줄. 교체 가능 | 소스에 박힘. 포크해야 교체 |
| 연결 | 이름표(`ctx.<key>`)로 간접 | `import`로 직접 |
| 확장 | 플러그인 한 줄, 제한 없음 | 정해진 슬롯에 꽂기 |
| 자기 개조 | 가능 (모델이 직접) | 불가 |
| 제품 규율 | 일부러 없음 | 기본 표면 증가를 CI로 차단 |
| 배울 것 | seam 3역 · 불변식 · 생성된 카탈로그 | 런타임 게이트 · provenance · 절제 |

**반면교사** `[gjc]`: ralplan은 `SKILL.md` 207줄, 최소 3 subagent, 최대 5회 루프로 매우 무겁다. 그래서 gjc는 항상 쓰지 않는다 — 모호한 실행 요청일 때만 자동으로 걸리고, 앵커(파일 경로·이슈 번호·심볼·번호 목록)가 하나만 있어도 통과시킨다. 같은 절제가 필요하다. 모든 요청에 전체 워크플로를 강제하면 안 되고, "언제 이 무거운 절차가 필요한가"를 판정하는 값싼 게이트를 앞단에 두되 그 판정도 LLM이 아니라 결정론적 앵커 검사여야 한다.

## 11. 아직 답하지 않은 것

- **그래프 스키마의 실물** — 노드 타입, 엣지 어휘, 끌 수 없는 고정 불변식 목록
- **STALE 전파 규칙** — 어떤 엣지가 전파를 옮기고 어떤 엣지가 막는가. 전파 깊이는 어디서 멈추는가
- **무거운 절차의 진입 게이트** — 언제 전체 워크플로를 돌리고 언제 건너뛰는가. ralplan식 앵커 검사의 스펙 설계 버전
- **형태(shape)의 정의** — DataFrame·텐서·dict 각각에서 무엇을 기록할지는 도메인 지식이라 기성품이 없다
- **cold-start 격리의 구체** — 정확히 무엇을 주고 무엇을 가리는가. worktree 구성, 결과 판정 방법
- **실험 · 스펙 · 랩을 한 형식으로 묶을지** — 셋이 같은 기계로 돈다면 매니페스트도 하나여야 하는가
