# 분해가 충분한가 — 독립 에이전트의 수렴성을 판정 기준으로

- 작성일: 2026-08-28
- 성격: **설계 제안.** 앞의 세 노트가 gajae-code를 세로로(단계별로) 팠다면, 이 문서는 가로로 자른다 — "분해는 어디서 일어나고, 충분한지 어떻게 아는가". 남의 하네스 분석이 아니라 **우리 하네스의 설계 결정**이므로 성격과 수명이 다르다. 확정되면 [`docs/prd.md`](../prd.md)로 승격한다.
- 배경 자료: [`deep-interview 해부`](./2026-08-28-deep-interview-ambiguity-scoring-and-revealed-preference.md) · [`ralplan 해부`](./2026-08-28-ralplan-consensus-harness-and-reviewer-sandbox.md) · [`ultragoal 해부`](./2026-08-28-ultragoal-execution-harness-and-evidence-gates.md)

## 1. 문제

> **"이 문제를 충분히 잘게 쪼갰는가?"를 어떻게 판정하나?**

"충분히 작다"에는 눈금이 없다. 그리고 이 질문은 [`deep-interview 해부`](./2026-08-28-deep-interview-ambiguity-scoring-and-revealed-preference.md) §6에서 다룬 "충분히 명확한가"와 같은 종류의 함정을 갖는다 — 관측 불가능한 절대량에 대한 판정을 요구하므로, 답을 숫자로 만들면 그 숫자는 검증 불가능한 자기평가가 된다.

---

## 2. gajae-code는 분해를 세 번 한다 `[gjc]`

먼저 사실 확인. 분해는 한 곳에서 일어나지 않고 **세 단계에서 각각 다른 축으로** 일어난다.

예시: *"CSV를 받아 정규화하고, 리뷰어가 승인하고, 감사 리포트를 내보내는 파이프라인"*

| 단계 | 축 | 기준 | 산출 |
| --- | --- | --- | --- |
| deep-interview (Round 0) | **결과물** | *"독립적으로 성공하거나 실패할 수 있는 것"* | `Ingestion` / `Normalization` / `Review UI` / `Export` |
| ralplan (Planner) | **변경과 순서** | *"Right-size the step count"* | `File-level changes` + `Sequencing and dependencies` |
| ultragoal (create-goals) | **검증 경계** | *"validation-coupled면 **합쳐라**"* | `G001` / `G002` … |

### 2.1 deep-interview는 구현 태스크를 명시적으로 배제한다

> *"구현 태스크나 필드는, 사용자가 독립된 결과물로 프레이밍하지 않는 한, 최상위 컴포넌트가 아니다."*

즉 1단계가 만드는 것은 **"무엇을 만드는가(what)"**의 목록이지 작업 목록이 아니다.

### 2.2 ralplan은 상류가 다 쪼갰다고 가정하지 않는다

세 역할 전부가 **스코프를 채우라**는 임무를 받는다:

| 역할 | 지시 |
| --- | --- |
| Planner | *"When input is thin, enrich it: … **surface missed sub-scope**"* |
| Architect | *"enrich thin plans with synthesis or **missed sub-scope**"* |
| Critic | *"when the plan is thin, **request concrete expansion** rather than only defects"* |

`[gjc]` **ralplan은 상류 분해를 못 미더워하는 것을 전제로 설계됐다.** 자연스럽다 — deep-interview는 의도적으로 구현을 보지 않으므로 구현 관점의 분해가 빠져 있는 것이 당연하고, 그것을 메우는 것이 ralplan의 일이다.

### 2.3 그런데 ultragoal은 오히려 합친다

> *"브리프를 얇은 스토리 여러 개로 쪼개기 전에, 후보들이 **validation-coupled**인지 확인하라. 그렇다면 하나의 goal로 병합하라."*

`[제안]` **이 규칙의 존재 자체가 상류 분해에 대한 자백이다.** 깔끔한 분할정복 트리가 아니라 **축을 바꿔가며 쪼갰다가 마지막에 다른 축으로 다시 합치는** 모양이다.

```
deep-interview  ──split──▶  ralplan  ──split──▶  ultragoal  ──merge──▶ …
   결과물 축                 변경/순서 축            검증 축
```

### 2.4 스코프 변경 권한은 단계마다 좁아진다

| 단계 | 권한 |
| --- | --- |
| deep-interview | **정한다.** 토폴로지 확정 + intent contract를 SHA-256으로 봉인 |
| ralplan | **넓힐 수 있다. 단 자백해야 한다.** post-interview에서 상류 스펙과의 모순·약화·확장을 나열하고 사용자에게 확인 |
| ultragoal | **재배열만.** `steer`로 쪼개고 합치되 집계 목표와 제약은 고정 |

### 2.5 그리고 ID 공간이 세 개인데 매핑이 없다 `[gjc]`

deep-interview는 토폴로지 확정 시 안정 ID를 만들어 SHA-256으로 봉인하고, 최종 spec에서 하나라도 빠지면 저장 자체를 실패시킬 만큼 엄격하게 지킨다. **그런데 그 ID가 하류로 넘어가지 않는다** — `intent_contract`는 deep-interview 모듈과 공용 인프라(ask 툴, state-runtime)에만 등장하고 ralplan·ultragoal 런타임에는 참조가 0건이다.

```
deep-interview:  surface:review, artifact:audit-report   (SHA-256 봉인)
                          ↓  (매핑 없음)
ralplan:         plan:cache-layer                        (계획 내부 ID)
                          ↓  (매핑 없음)
ultragoal:       G001, G002, G003                        (스토리 ID)
```

ralplan의 post-interview가 하는 상류 대조도 **산문 인용**이다 — *"해당 아티팩트와 라인/섹션을 인용하라."* 기계가 검사할 수 있는 링크가 아니다.

`[제안]` **결과: `surface:review`가 실제로 구현됐는지를 자동으로 확인할 방법이 없다.** 각 단계 안에서는 해시까지 써가며 엄격한데 단계 사이는 비어 있다. 이것이 우리 추적성 검증기가 채울 자리이며, [`skill-vs-harness`](./2026-08-19-skill-vs-harness.md) §7.2가 말한 "이 프로젝트의 백테스터"의 실증이다.

### 2.6 되먹임 경로가 없는 이유

파이프라인은 단방향이다 (`pipeline: [deep-interview, ralplan]`). ralplan이 *"토폴로지 분해 자체가 틀렸다"*를 발견해도 deep-interview를 다시 열 수 없고, 자기 안의 `ask` 한 번으로 때운다.

`[제안]` **왜 그런가 — 되돌릴 근거를 만드는 방법이 없기 때문이다.** LLM의 인상으로는 상류 재개를 정당화할 수 없다. ultragoal의 `steer`가 *"광범위한 자연어 요청은 추측하지 않고 거부한다"*고 못 박은 것도 같은 이유다. **되돌림에는 증거가 필요하다는 원칙은 이미 있는데, 그 증거를 만드는 기계가 없다.**

## 3. 제안 — 충분성을 수렴성으로 측정한다 `[제안]`

> **분해의 충분성은 조각의 크기가 아니라 그 조각의 식별력(identification)이다. 그리고 식별력은 독립 에이전트들의 결정이 수렴하는지로 측정한다.**

직관 비유: **레시피가 충분히 자세한지는 요리사 5명에게 똑같은 레시피만 주고 각자 만들게 해보면 안다.** 5개가 같으면 충분한 것이고, 제각각이면 뭔가 빠진 것이다.

### 3.1 이것이 이 프로젝트에서 세 번째로 두는 같은 수다

| | 못 재는 것 | 대신 재는 것 |
| --- | --- | --- |
| deep-interview 비판 | "이 요구사항이 얼마나 모호한가" | 같은 증거 상태에서 **순위가 뒤집히는가** (WARP) |
| ralplan 비판 | "이 리뷰 판정이 옳은가" | 지적이 해소됐는데 **평결이 나빠지는가** (단조성) |
| **이 문서** | **"이 분해가 충분한가"** | **독립 실행이 수렴하는가** |

셋 다 **관측 불가능한 절대량을 포기하고 관측 가능한 일관성 속성으로 갈아타는** 동일한 수다. 그리고 셋 다 결정론적으로 계산 가능하다 — LLM 판단이 들어가지 않는다.

## 4. 계량경제 프레임 — 식별(identification) `[econ]`

스펙을 제약, 구현을 미지수로 놓으면 정확히 대응한다.

| 상태 | 방정식 | 에이전트들이 하는 일 |
| --- | --- | --- |
| **과소식별** | `x + y = 10` — 해 무수히 많음 | **발산.** 각자 다른 해를 고름 |
| **정확식별** | `x + y = 10, x − y = 2` — 해 유일 | **수렴** |
| **과잉식별 + 모순** | `x + y = 10, x − y = 2, x = 7` — 만족하는 해 없음 | **각자 다른 제약을 희생하며 발산** |

`[제안]` 세 번째가 특히 값지다. **사람은 스펙을 읽어서 모순을 잘 못 찾는다.** 그런데 *"A는 이 제약을 포기했고 B는 저 제약을 포기했다"*는 관찰은 **모순의 위치를 정확히 짚어준다.**

따라서 발산 패턴이 두 가지 다른 병을 구분해준다:

- **정보가 없어서** 갈라짐 → 과소식별 (스펙을 채워야 함)
- **정보가 모순돼서** 갈라짐 → 과잉식별 검정 실패 (스펙을 고쳐야 함)

---

## 5. 발산은 하나의 신호가 아니다 — 네 얼굴 `[제안]`

**가장 실용적인 부분.** "발산했으니 더 쪼개자"는 네 경우 중 하나에서만 옳다.

| 발산 양상 | 진단 | 처방 |
| --- | --- | --- |
| 전원이 **같은 정보**를 요구 | 명세 부족 (과소식별) | **채워라.** 쪼개면 같은 구멍이 양쪽에 복제될 뿐 |
| **서로 직교하는 축**에서 갈림 | 조각이 너무 큼 | **그 축을 따라 쪼개라** |
| 각자 **내적으로 완결**됐는데 서로 다름 | 열린 설계공간 | **사람이 결정.** 쪼개도 사라지지 않음 |
| 전원이 **형제 조각을 참조** | 결합돼 있음 | **합쳐라** (ultragoal의 validation-coupled 규칙) |
| 각자 **다른 제약을 희생** | 스펙 내부 모순 | **스펙을 고쳐라** |

### 5.1 그리고 여기서 가장 강한 결과가 나온다

> **발산의 축이 곧 분할선이다.**

에이전트 A는 인증 방식에서, B는 저장 형식에서 갈렸는데 그 둘이 서로 무관하다면, 그 조각은 **독립적인 결정 두 개를 품고 있다.** 그것이 정확히 쪼개야 할 자리다.

`[제안]` **어디서 쪼갤지 추측할 필요가 없다 — 불일치가 알려준다.** deep-interview는 사람에게 물어 토폴로지를 정하는데, 사람은 머릿속으로 **결과물**을 나누지 구현이 얼마나 얽혔는지는 모른다 (§2.1). 이 방법은 **측정으로 정하므로** 사람 직관이 놓친 결합을 잡아낸다.

## 6. 무엇을 비교하나 — 구현이 아니라 결정 집합 `[제안]`

**문제:** 조각마다, 수정할 때마다 N개 에이전트에 구현을 시키면 비싸다. 그리고 코드는 diff해도 의미가 없다 — 다르게 짜도 등가일 수 있다.

**해법: 구현시키지 말고 결정 목록만 받는다.**

각 레인에 이것만 요구한다:

```json
{
  "chunk_id": "surface:review",
  "spec_hash": "sha256:...",
  "decisions_required": [
    { "id": "approval-quorum", "my_choice": "1명",
      "basis": "inferred",  "note": "스펙에 없어 추론" },
    { "id": "csv-encoding",    "my_choice": "UTF-8",
      "basis": "specified", "ref": "spec §3" }
  ],
  "external_refs": ["Normalization 조각의 스키마 정의 필요"],
  "unresolvable": ["에러 레코드를 버리는지 표시하는지 결정 불가"],
  "sacrificed_constraints": []
}
```

그리고 **이것끼리 비교한다.**

| 장점 | |
| --- | --- |
| **싸다** | 구현 대신 읽고 목록만 산출 |
| **바로 진단된다** | `basis: "inferred"` 다수 → 과소식별 · `external_refs`가 형제를 가리킴 → 결합 · `unresolvable` 겹침 → 열린 설계공간 · `sacrificed_constraints` 상이 → 스펙 모순 |
| **비교가 결정론적** | 코드 등가성 판정은 어렵지만 **결정 ID 집합 비교는 집합 연산** |
| **기존 개념과 접점** | deep-interview도 auto-answer를 confidence와 함께 추적하고 "가정에만 기댄 비율"을 floor에 반영한다. 같은 개념을 조각 단위로 옮기는 것 |

`[제안]` **재는 것은 "구현의 수렴"이 아니라 "결정 집합의 수렴"이다.** 구현이 달라도 상관없다 — **결정이 갈리는 것이 문제다.**

## 7. 다양성 요건과 함정 `[제안]`

### 7.1 같은 모델 N개는 같이 틀린다

같은 모델 + 같은 프롬프트 + 같은 컨텍스트로 N번 돌리면 수렴은 거의 자동으로 나오고, **그 수렴은 아무것도 측정하지 않는다.** 온도가 낮다는 뜻일 뿐이다. 스펙이 좋아서가 아니라 **모델이 같은 편향을 공유해서** 수렴한 것이다.

gajae-code는 이것을 알고 있다. 두 군데서 같은 대비를 한다 `[gjc]`:

- deep-interview 패널: **다른 페르소나** + *"각자 자기 컨텍스트 사본을 받아 서로의 프레이밍에 anchoring하지 않게"*
- ultragoal 코호트: **다른 렌즈** (cleaner / architect / qa)

**둘 다 "복제"가 아니라 "다양성"이다.**

### 7.2 원칙: 정답과 무관한 축에만 다양성을 넣는다

다양성을 너무 넣으면 스펙과 무관한 이유로 발산해 신호가 노이즈에 묻힌다.

```
반드시 동일:  스펙 내용, 제약, 수용 기준        ← 해시로 잠금
달라도 됨:    역할·렌즈, 컨텍스트 제시 순서, 모델, 온도
```

`sourceHash` 동결(§8)이 정확히 앞줄을 보장하는 장치다 — **"관련 축은 비트 단위로 동일함"을 해시로 증명하고 다양성은 그 바깥에만 넣는다.**

## 8. 재사용할 프리미티브와 새로 써야 할 것 `[gjc]` `[제안]`

### 8.1 그대로 가져올 것 — `sourceHash` 동결

ultragoal 경계 게이트의 코드 강제:

```
레인 해시 ≠ 코호트 해시  →  판정 거부
  "every lane must inspect the same immutable source"
```

**"다들 비트 단위로 같은 것을 봤다"를 주장이 아니라 증명으로 만드는 장치.** §7.2의 요건을 정확히 충족한다.

### 8.2 ★ 중요한 함정 — 기존 기계는 반대 가정 위에 있다

ultragoal 코호트의 다른 두 규칙:

```
❌ 같은 세대에 두 번째 architect나 qa 레인은 거부된다
❌ priorGenerationSourceHash == sourceHash 이면 거부 (같은 소스 재검토 금지)
```

**둘 다 "같은 입력에 반복 실행"을 금지한다.** 그런데 이 제안은 정확히 그것을 해야 한다.

`[제안]` **따라서 두 종류의 레인을 구분해서 설계해야 한다:**

| | **검증 레인** (verification) | **측정 레인** (measurement) |
| --- | --- | --- |
| 레인의 성격 | 서로 다른 렌즈 | 같은 일의 복제 |
| 여러 개인 이유 | **커버리지** — 각자 다른 위험을 봄 | **측정** — 흩어지는 정도가 신호 |
| 중복은 | **낭비** (거부됨) | **목적** (많을수록 신호 향상) |
| 결과 판정 | 전원 통과해야 함 (AND) | 얼마나 일치하나 (분산) |
| 실행 횟수 | 1회, 중복 금지 | N회, 포화까지 |

**동결 프리미티브는 공유하되 그 위의 조인 규칙은 새로 써야 한다.** 이 구분 없이 기존 코호트 기계를 재사용하면 "두 번째 레인은 거부됨"에 막힌다.

---

## 9. 종료 조건 — 임계값이 아니라 포화 `[제안]`

**경고: 여기서 임계값을 만들면 안 된다.** "수렴률 95% 이상 통과" 같은 기수 임계값은 [`deep-interview 해부`](./2026-08-28-deep-interview-ambiguity-scoring-and-revealed-preference.md) §7의 함정(임계값 0.05가 도달 불가능해 우회로로 나가는)을 그대로 재현한다.

두 가지 중 하나로 간다:

**(a) 이진 판정** — 발산 축의 개수가 0인가. 축은 세면 나오는 정수다.

**(b) 포화 판정** — **레인을 하나 더 추가해도 새로운 발산 축이 나오지 않는가.**

(b)가 낫다:

- **N을 미리 정할 필요가 없다.** 새 축이 안 나올 때까지 늘리면 된다
- **이 프로젝트에서 이미 세 번 도달한 결론과 같은 모양이다** — deep-interview의 ontology stability(엔티티가 더 안 바뀌는가), 이 프로젝트가 제안한 순위 안정성(더 물어도 순서가 안 바뀌는가), 그리고 지금의 포화. **전부 "포화"지 "임계값"이 아니다**

> **"충분한가?"를 물으면 임계값이 필요해지고, "더 해도 안 바뀌나?"를 물으면 필요 없어진다.**

## 10. 되먹임과의 연결 `[제안]`

§2.6에서 본 문제 — **되돌릴 근거를 만드는 방법이 없어서 파이프라인이 단방향이 됐다.** 수렴성 측정이 그 근거를 만든다.

```
조각 "surface:review" — 5개 레인 실행 (spec_hash 동일 확인됨)

발산 축 2개:
  (a) 승인 정족수      — 3:2로 갈림, 5개 전원 basis: "inferred"
  (b) 코멘트 저장 위치 — 4개가 external_refs로 Normalization 조각을 지목

진단: (a) 과소식별 → 스펙 보강
      (b) 결합     → Normalization과 병합 검토

→ 상류 되먹임 발행 (증거: 5개 레인의 결정 집합 + spec_hash)
```

**이것은 인상이 아니라 관측이다.** 그리고 관측이면 되돌림을 정당화할 수 있다.

### 10.1 되먹임 설계는 `steer`의 5종 세트를 따른다 `[gjc]`

ultragoal이 이미 완성해둔 형태를 그대로 가져온다:

1. **타입 고정** — 허용된 변형만 (우리 경우: `enrich_spec` / `split_chunk` / `merge_chunks` / `escalate_decision` / `annotate`)
2. **자연어 거부** — "좀 바꿔줘"는 상태를 바꾸지 못함
3. **evidence + rationale 필수**
4. **거부된 시도도 기록**
5. **하드 삭제 금지** — 대체된 조각은 메타데이터와 함께 남고 스케줄링에서만 빠짐

### 10.2 그리고 예산 `[gjc]`

ultragoal의 `review_blocker` 재귀 상한 3. **되먹임 경로를 여는 순간 순환 가능성이 생기므로, 여는 것과 예산을 정하는 것은 한 세트다.**

## 11. 설계 요약

| | |
| --- | --- |
| **판정 대상** | 조각의 크기가 아니라 **식별력** — 이 조각만 보고 답이 하나로 정해지는가 |
| **재는 것** | 구현이 아니라 **결정 집합** (`decisions_required` / `external_refs` / `unresolvable` / `sacrificed_constraints`) |
| **동일성 보장** | 스펙을 동결하고 해시 (`sourceHash` 패턴 재사용) |
| **다양성 주입** | 정답과 무관한 축에만 (렌즈·순서·모델·온도) |
| **종료 판정** | 발산 축 개수 0, 또는 **레인 추가 시 포화** |
| **진단** | 발산의 다섯 얼굴 → 채우기 / 쪼개기 / 사람 결정 / 합치기 / 스펙 수정 |
| **분할선** | **발산의 축이 곧 분할선** |
| **되먹임** | 발산 기록이 곧 상류 되돌림의 증거. 타입 고정 + evidence + 예산 |
| **레인 구분** | **검증 레인(1회, AND)과 측정 레인(N회, 분산)을 분리** |

## 12. 미해결 질문

- **비용.** 조각당 N개 레인 × 조각 수 × 수정 횟수. 결정 목록만 받아 완화하지만 여전히 곱셈이다. 어느 시점에 측정을 돌릴지(매 수정마다? 조각 확정 시 1회?)가 미정
- **다양성의 양.** §7.2의 "무관한 축에만"은 원칙이고 구체 파라미터가 없다. 모델을 섞으면 비용과 결과 해석이 복잡해지고, 렌즈만 바꾸면 다양성이 부족할 수 있다
- **`decisions_required`의 ID 안정성.** 레인 A의 `approval-quorum`과 레인 B의 `who-approves`가 같은 결정인지 판정하는 문제. **이것이 해결되지 않으면 집합 비교가 성립하지 않는다** — 가장 중요한 미해결 항목. deep-interview의 ontology 매칭(이름이 달라도 type + 필드 50% 겹치면 동일 개체로 판정)이 참고 선례
- **열린 설계공간(§5 세 번째 행)의 자동 판정.** "각자 내적으로 완결됐다"를 어떻게 기계가 아는가. 사람 판단이 필요할 수 있고, 그렇다면 그 경로도 설계에 있어야 한다
- **측정 결과의 보존 형태.** 세 노트가 공통으로 지적한 실수 — **판단의 이력을 버리지 말 것.** 발산 기록은 최신값이 아니라 시퀀스로, 각 판정에 `spec_hash`를 붙여 저장해야 한다
